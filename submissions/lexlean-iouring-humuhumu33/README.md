# LexLean + C: a proved core on io_uring and SQLite B-tree reads

Every file here is written by one [LexLean](https://github.com/UOR-Foundation/LexLean) program, compiled to the plain Lean in `lean/`. On the box, official Lean checks its theorems, runs it, and stops the build unless what it writes matches these files. Six decisions are written and proved in LexLean (`core.lex`) and reach the server as about 100 lines of C tables. **Everything else is hand-written C in `src/server.c`, carried as text through that program, because LexLean has no I/O or raw pointers: the event loop, parsers, JWT, SQLite calls, and the logic that picks which table to ask and when. The server as a whole is not formally verified.**

| | |
|---|---|
| Language | LexLean 0.3.0, compiled to Lean 4.32.1, for the core and for writing the files; C (gnu11) for everything that touches a socket or a pointer |
| Framework | none |
| Compiler | Official Lean 4.32.1 (SHA-256 pinned); GCC from `build-essential`, profile-guided, `-O3 -march=x86-64-v3` |
| io_uring | liburing 2.5 from Ubuntu 24.04, version pinned, linked statically |
| SQLite | 3.54.1 amalgamation, SHA-256 pinned, not patched, compiled into one translation unit with the server |
| **Nginx or direct** | **Direct** on `HOST:PORT` |

## What is proved, tested, and neither

| Part | Status |
|---|---|
| Batch order: a batch's responses leave only after its commit, and are replaced by failures only when it fails. Per-request errors (400, 401, 404) go out with the batch | Proved over every phase and event |
| Routes: only POST writes, every write needs a token, an unknown method is not found. Which route becomes which handler is C | Proved over every method and path shape |
| The hold table: no read is held on a connection with nothing held, every write is held at a closed gate, and every later request on a held connection is held, while the queue has room. That the C then keeps order is not proved | Proved over every input |
| The write pause: closes at its limit, stays closed until the log is copied or the wait times out | Proved over every input |
| The failure table: only an internal failure is a 5xx. The 503 from `/health` and the fallback 500 are hand-written | Proved over every failure |
| JSON byte classes | Proved at bytes 0, 31, 32, 34, 92 and 255 only |
| The tables as they reach C, all 256 byte classes, the 8-byte escape test | Tested exhaustively, not proved |
| The event loop, HTTP and JSON parsing, JWT, B-tree reads, SQLite calls | C. Not proved. Covered by `test/test.sh` and load runs |

The theorems are about the LexLean definitions. Nothing proves that the C uses a table correctly, or asks it at the right time: a repository test reads the source for that, and the 42 tests exercise it. The registered claims and planted defects are in [the repository](https://github.com/humuhumu33/uor-12USDserver).

## How it is built

`install.sh` installs official Lean 4.32.1, pinned by digest, about 2.8 GB on disk and used only by the build. `build.sh` then:

1. runs `lake build --wfail` in `lean/`. This checks the 22 theorems in the module, and `Claims.lean`, which restates them directly on the functions and checks each one's axioms. A false, weakened or deleted theorem, a `sorry` or an added axiom stops the build;
2. runs the program, and stops if any file it writes differs from the file here, `src/server.c` and `src/core.h` included;
3. tests the tables against rules written out independently in `src/core_test.c`;
4. compiles `src/` with SQLite, downloading and checksumming SQLite.

`src/` and `core.lex` are here to read. `lean/UorEmit/Emit.lean` holds that same C as string literals, so a review should read `src/`, and the build proves the two match. `Emit.lean` and `lean/LexLeanRuntime/Portable.lean` are generated by LexLean 0.3.0, which has no standalone release, from `.lex.tex` source in the repository. **They are compiler output committed here, and I'm stating that plainly for rule 10.** `Portable.lean` is LexLean's runtime, MIT or Apache-2.0. No binary is shipped.

## Design

One thread runs the event loop, HTTP, JWT, JSON and SQLite reads. A second thread only runs WAL checkpoints.

- **Sockets.** Direct descriptors, so `LimitNOFILE=65535` caps one ring's table and not the server. Up to 8 rings, made as connections need them. Eight `SO_REUSEPORT` listeners.
- **Reading.** A multishot receive into provided buffers, 4,096 x 1 KB per ring, one submission fewer per request than a poll and a read. A receive that ends when buffers run out isn't re-armed at once: its socket gets single reads in bounded rounds until it is empty, the fix #264 measured on real droplets.
- **Drain first.** Requests are read out of their sockets as soon as they arrive, into a queue of up to 32,768, and answered up to 2,048 per batch. A request waiting in a socket costs 3-4 KB of network buffer; read out, it costs about 100 bytes.
- **Batches.** Each batch is one SQLite transaction: reads from its snapshot, then writes through prepared statements, then `COMMIT`, then every response. No response leaves before its commit (rule 6).
- **Reads** walk SQLite's own B-tree cursors inside that transaction, with no SQL engine and no remembered data: the organiser allowed this for #153. The feed walks `posts_created_at_id_idx`, seeks the 20 posts, and counts likes with one range walk where it can. Every request reads SQLite while it is served (rule 5).
- **JWT.** Every token's signature is verified on every request. The HMAC key's pad states are hashed once at startup.
- **WAL.** `synchronous=NORMAL`, `wal_autocheckpoint` off. A checkpoint thread at nice 19 runs passive checkpoints past 1,000 frames. Past 4,000, writes wait for at most 1 s while reads go on, so the next write can restart the log. Past 16,384 the loop checkpoints itself. A commit's frames go to the kernel in one `pwrite`, through a small VFS shim over `unix-excl`.
- **Page cache.** 32 MB, with `mmap_size=0`.
- **Code lock.** The binary is locked in RAM, so reclaim at the memory wall can't stall the loop on its own code.

## Known limits

- A pipelined write and read in one batch: reads run first, so the read sees the state before the write. Requests on a connection are otherwise answered in order.
- If the hold queue is full, a later request on a held connection can overtake a held one.

## Measurements

No user-count score is claimed. The organiser's benchmark is the only score.

Measured in a guest shaped like the box: 1 vCPU, 1,967 MB, no swap, Ubuntu 24.04 on kernel 6.8.0-147, with the entry installed and built inside the guest, on GitHub's runners. A replay of the `bench/load.js` user model runs on the host across a virtio network device, as in #278. The build in the guest took 69-116 s and 1.44 GB at its peak. Each step was a 60 s ramp and a 2-minute hold, one run per load, on a freshly booted guest. The runner's host CPU changes the result a great deal, so both hosts are shown.

| Users | EPYC 9V45 host | EPYC 9V74 host, two runs |
|---:|---|---|
| 280,000 | held, p99 5.8 ms | held, p99 8.7 ms |
| 300,000 | held, p99 6.2 ms | held, p99 363 and 45 ms |
| 310,000 | held, p99 5.9 ms | held, p99 97 ms |
| 320,000 | held, p99 194 ms | **killed by out-of-memory**, twice |

Every run that finished had 0 errors. Against c-iouring-pavlyhalim (#245), run in the same guest right after ours, latency was level in three of the four paired runs at 300,000 and above. In the first 9V74 run ours was worse at 300,000 (p99 363 ms against 115 ms). On the 9V74 host at 320,000, ours was killed and #245 collapsed to a p95 of 26 s without dying, so both fail a hold there. Ours used 6-500 MB less memory at its peak, in every pair.

The kill at 320,000 is the main open risk. Past what the CPU can serve, requests pile up in sockets at about 130 MB a second, and the server itself holds only about 125 MB when it is killed. Whether the real box behaves like the faster host or the slower one is unknown.
